# 模块

模块（module）是 Go 依赖管理和版本控制的基本单元。一个模块由其根目录下的 `go.mod` 文件定义，其中声明了该模块的唯一标识、Go 版本要求和依赖模块等。

一个模块通常对应一个项目，其中可以包含若干个库包（可被 `import` 的非 `main` 包）、若干个应用程序包（`main` 包），或者二者兼有。

核心命令：

| 命令 | 作用 | 关键输出文件 |
| --- | --- | --- |
| `go mod init <module-path>` | 初始化模块 | `go.mod` |
| `go mod tidy` | 自动整理依赖模块 | `go.mod`、`go.sum` |
| `go mod download` | 下载依赖模块到模块缓存目录 | - |
| `go mod verify` | 验证已下载的依赖模块的校验和 | - |
| `go mod vendor` | 创建 `vendor` 目录，用于离线构建 | `vendor/` |
| `go mod edit` | 以命令行方式编辑 `go.mod` 文件 | `go.mod` |

## go.mod 文件

在要作为模块根目录的目录（通常是项目根目录）执行 `go mod init <module-path>` 初始化模块，即可生成 `go.mod` 文件。

模块路径（module-path）是模块的唯一标识，它是一个字符串，不要求必须对应真实 URL。但惯例上使用可解析的域名路径格式：`<域名>/<作者>/<项目>`，例如 `github.com/yourname/your-proj`，便于未来发布和通过 `go get` 获取。

从 `v2` 版本开始，主版本号必须写入模块路径，例如 `github.com/yourname/your-proj/v2`，所以 `.../your-proj` 和 `.../your-proj/v2` 是两个不同的模块。

`go.mod` 是模块定义文件，内容如下（示例）：

```text
// 模块路径，是模块的唯一标识，也是该模块内所有包的导入路径前缀
module github.com/yourname/your-proj

// 模块要求的最低 Go 版本
go 1.24.1

// 依赖模块及其版本
require (
 github.com/gin-gonic/gin v1.12.0
 golang.org/x/text v0.42.0
)

// 本地替换，见「05 多模块开发」中的 call-module 示例
replace golang.org/x/text => ../local/text

// 排除模块特定版本，禁止其被 MVS 选中（不常用）：go mod edit -exclude=github.com/somebody/some-proj@v1.0.0
exclude github.com/somebody/some-proj v1.0.0

// 依赖的命令行工具（Go 1.24 引入）
tool golang.org/x/tools/cmd/stringer // 记录的是工具 main 包的包路径

// 间接（indirect）依赖的模块及其版本
require (
 golang.org/x/mod v0.41.0 // indirect
 golang.org/x/sync v0.23.0 // indirect
 golang.org/x/tools v0.50.0 // indirect
)
```

Go 模块版本号采用语义化版本：`v主版本号.次版本号.修订号`，例如 `v1.12.0`；预发布版本在修订号后附加标识，例如 `v1.12.0-rc.1`；伪版本由 `go get` 根据未打标签的提交自动生成，例如 `v0.0.0-20261019120000-abcdef123456`。

预发布版本号格式为 `v主版本号.次版本号.修订号-标识符[.数字]`，常见的预发布标识符有 `alpha`、`beta`、`rc`、`pre` 等；数字后缀是可选的，一般从 0 开始。

### go 指令和 toolchain 指令

`go.mod` 中的 `go` 指令声明模块要求的最低 Go 版本，`toolchain` 指令（Go 1.21 引入）指定主模块（正在其中执行 `go` 命令的那个模块）建议使用的工具链版本，例如 `toolchain go1.25.0`。

构建时 Go 依据 `toolchain` 指令（建议版本）和 `go` 指令（最低要求）取版本较高者确定所需工具链；默认策略 `GOTOOLCHAIN=auto` 下，若该版本高于当前 `${GOROOT}` 目录中的 Go 工具链版本，则自动下载并切换到对应工具链。

`toolchain` 指令只在主模块的 `go.mod` 中被读取和生效。当把某个库作为依赖引入当前项目时，这个库的 `go.mod` 中即使写了 `toolchain`，也不会影响当前项目的构建工具链选择。

向 `go.mod` 中添加 `toolchain` 指令：`go mod edit -toolchain=go1.25.0`。`toolchain` 指定的版本低于 `go` 指令声明的版本时不会生效，工具链选择仍以 `go` 指令的要求为准。

从 `go.mod` 中移除 `toolchain` 指令：`go mod edit -toolchain=none`，`none` 表示移除。

执行 `go mod tidy -go=1.25` 可更新 `go` 指令声明的最低 Go 版本并重新同步依赖，`go mod edit -go=1.25` 只修改 Go 版本号而不同步依赖。

### require 指令和 replace 指令

当通过 `go get` 添加依赖模块时，会自动更新 `go.mod` 中的 `require` 指令。`require` 指令记录的是依赖模块的精确版本号（不是范围）。

`require` 指令中的 `indirect` 注释表示间接依赖，即未在项目源码中直接导入（import）、因为被其他依赖引用而引入的模块。

执行 `go mod tidy` 自动整理直接依赖和间接依赖。

通过 `replace` 指令将某个依赖模块替换为本地副本或 fork 版本，语法为 `-replace=old[@v]=new[@v]`，例如：

```bash
# 用本地副本替换：模块路径[@版本号]=本地路径
go mod edit -replace github.com/somebody/some-proj[@v1.0.0]=/path/to/local/some-proj

# 用 fork 版本替换：模块路径[@版本号]=fork仓库地址@版本号
go mod edit -replace github.com/somebody/some-proj[@v1.0.0]=github.com/yourfork/some-proj@v1.0.1
```

### tool 指令（Go 1.24 引入）

在 Go 1.24 之前，Go 缺少统一的标准方式来管理代码生成器、linter 等开发工具，常见的做法是创建一个 `tools.go` 文件，通过空白导入（`import _ "..."`）使这些工具被记录为项目的依赖，例如：

```go
//go:build tools

package tools

import (
 _ "golang.org/x/tools/cmd/stringer"
)
```

Go 1.24 引入的 `tool` 指令让声明工具依赖变得像声明普通库依赖一样直接，其核心是将工具作为项目依赖模块进行版本化管理，确保团队所有成员使用完全相同的工具版本。

[stringer](https://pkg.go.dev/golang.org/x/tools/cmd/stringer) 是 Go 官方 [x/tools](https://pkg.go.dev/golang.org/x/tools) 仓库中的一个常用代码生成工具，它会根据给定类型自动生成 `String()` 方法以实现 `fmt.Stringer` 接口。下面以 `stringer` 为例，介绍对工具的管理操作。

添加工具：`go get -tool golang.org/x/tools/cmd/stringer@latest`，这条命令会把 `stringer` 的最新版本源码连同其依赖一起下载到模块缓存目录，并在 `go.mod` 中添加相应的 `require` 和 `tool` 指令。它不会编译或安装可执行程序，而是在通过 `go tool` 运行工具的时候按需构建二进制文件并执行，结果缓存在 `${GOCACHE}` 目录，不写入 `${GOBIN}` 目录。

`golang.org/x/tools/cmd/stringer` 是工具 `main` 包的完整包路径，`go.mod` 中的 `tool` 指令记录的就是它；包路径的最后一段 `stringer` 是工具的默认二进制名。

假设项目中有如下 `color.go` 文件，其中定义了一个枚举类型 `Color`：

```go
type Color int // 自定义 Color 类型

const (
    Red   Color = iota // 0
    Green              // 1
    Blue               // 2
)
```

使用工具：`go tool golang.org/x/tools/cmd/stringer -type=Color`，工具名可简写为其包路径的最后一段 `stringer`。这条命令会生成 `color_string.go` 文件，其中包含 `func (i Color) String() string` 方法。

`go tool` 命令语法为 `go tool <tool-name> <args>`，`go tool` 只负责定位并构建工具的二进制文件，工具名之后的所有参数原样透传给工具本身。所以 `-type=Color` 是发给 `stringer` 的，不是 `go tool` 的选项，`go tool` 自己的选项如 `-n` 必须写在工具名之前。

`stringer` 也常与 `//go:generate` 注释配合，由 `go generate` 命令自动调用，详见「06 Go 工具链」。

查看当前可用的所有工具：`go tool`

从 `go.mod` 中移除工具：`go get -tool golang.org/x/tools/cmd/stringer@none`，`@none` 表示移除。

升级所有工具：`go get tool`，这里的 `tool` 是 Go 的保留名（reserved name），展开为 `go.mod` 中 `tool` 指令声明的所有工具。

将 `go.mod` 中 `tool` 指令声明的所有工具编译并安装到 `${GOBIN}` 目录以便全局使用：`go install tool`。

## go.sum 文件

`go.sum` 文件记录模块依赖图中各模块的校验和（以本地路径 `replace` 替换的模块除外），用于验证模块内容的完整性。

每个模块版本（同一模块可能以多个版本出现在 `go.sum` 中）通常对应两行记录：一行记录模块压缩包的校验和；另一行的版本号带 `/go.mod` 后缀，记录该模块 `go.mod` 文件的校验和。仅出现在依赖图中、构建时无需下载压缩包的模块版本，可能只有 `/go.mod` 一行。示例：

```text
github.com/bytedance/sonic v1.9.1 h1:ei0tVql02GmiYGRCTUcI6g...
github.com/bytedance/sonic v1.9.1/go.mod h1:iZcSUejdk5C4OW...
```

`go build`、`go vet` 等命令在解析、下载依赖模块时自动验证校验和，不一致则报错。也可执行 `go mod verify` 手动验证本地模块缓存中模块的完整性。

## 依赖管理

### go get 添加依赖

通过 `go get` 添加依赖模块到 `go.mod`，并自动更新 `go.mod` 中的 `require` 指令：

- 指定版本：`go get github.com/BurntSushi/toml@v1.2.0`
- 最新版本：`go get github.com/BurntSushi/toml`，省略版本号等价于 `@latest`
- `go get .`：为指定包添加所有依赖，这里的 `.` 表示当前目录下的包

也可以获取依赖模块的指定分支或提交：

- `go get example.com/theirmodule@branch-name`：获取指定分支
- `go get example.com/theirmodule@commit-hash`：获取指定提交

标准库的包不需要 `go get` 添加依赖，直接导入包即可使用。

CI/CD、Docker 构建等需要预先准备环境，可以执行 `go mod download` 将依赖提前下载到模块缓存目录。

### go get -u 更新依赖

`go get -u` 只更新模块的次版本和修订版本，不会自动跨越主版本（因为 `v2+` 版本是不同的模块）；`go get -u=patch` 更保守，只更新修订版本。

`go get -u` 在更新目标模块的同时，还会更新这些模块的依赖（含间接依赖）。

- 更新模块及其依赖：`go get -u github.com/BurntSushi/toml`
- `go get -u ./...`：更新当前目录下所有源文件中 `import` 的直接依赖及其间接依赖

注意：Go 将 `v2+` 版本视为不同的模块，在升级时需手动 `go get` 并修改源文件中的 `import` 语句。

### go mod tidy 整理/同步依赖

在项目根目录执行 `go mod tidy`：

- 添加缺失模块：自动扫描所有源文件中的 `import` 语句，将构建所需但尚未记录的依赖模块添加到 `go.mod` 文件
- 移除未引用模块：删除 `go.mod` 文件中不再被任何源码引用的依赖模块
- 同步校验文件：同时整理 `go.sum` 文件，添加缺失的校验和记录，移除多余的条目，确保依赖的完整性

建议在修改 `import` 语句后、构建部署前或定期执行 `go mod tidy`，以保持依赖整洁。

### 清理模块缓存并重新下载依赖

当模块缓存损坏或需要强制重新下载依赖时，在项目根目录执行：

```bash
go clean -modcache
go mod tidy
```

`go clean -modcache` 会清空整个模块缓存目录（`${GOMODCACHE}`），`go mod tidy` 随后按 `go.mod` 重新下载并同步依赖。

### 查询依赖

| 命令 | 说明 |
| --- | --- |
| `go list -m all` | 列出所有模块及其版本（含主模块和间接依赖）。展示的是 MVS 最终选择的版本 |
| `go list -m -u all` | 列出所有模块及其最新版本（如果有的话） |
| `go list -m -versions <module>` | 查看指定模块的所有版本，示例：`go list -m -versions github.com/gin-gonic/gin` |
| `go list -m <module>` | 查看指定模块的当前版本 |
| `go list -m -u <module>` | 查看指定模块的当前版本及最新版本（如果有的话） |
| `go mod graph` | 查看模块依赖关系，每行两个字段，用空格分隔，前者依赖后者。展示的是原始依赖声明（`go.mod` 中的 `require` 指令），并非 MVS 最终选择的版本 |
| `go mod why <pkg>` | 查看主模块到该包的最短导入路径，输出一条从主模块出发，经过一系列包，最终到达目标包的链路。可查清指定包是在哪里被导入的 |
| `go mod why -m <module>` | 查看主模块到该模块中任意包的最短导入路径。可查清模块是在哪里被引用的 |

### 版本管理最佳实践

- 生产环境锁定确切版本，确保每次构建内容一致
- 定期更新依赖版本：`go get -u ./...`
- 保持依赖整洁：`go mod tidy`

## MVS 版本选择算法

Go 使用最小版本选择（MVS，Minimal Version Selection）算法，为本次构建计算出一份实际使用的模块版本清单，称为构建列表（build list）。它不是 `go.mod` 里的 `require` 声明，而是 MVS 对所有版本约束取最高版本后得到的最终结果，可用 `go list -m all` 查看。

MVS 算法：

- 从主模块出发，遍历整个模块依赖图
- 对每个模块，收集所有 `require` 声明的版本约束
- 选取其中最高的版本，作为该模块在构建列表的版本

例如，项目直接依赖模块 A 和 B，A 和 B 都依赖模块 C，并且 A 依赖 C 的 v1.1.0、B 依赖 C 的 v1.0.0。`require` 记录的是最低版本要求，不低于要求即可满足，所以 MVS 会为 C 选择两者中较高的 v1.1.0。换言之，MVS 并非选取模块的“最小版本号”，而是选取能满足所有 `require` 约束的“最小可满足版本”（即所有约束中的最大版本），“最小版本选择”之名也源于此。

## 离线构建（vendor）

在项目根目录执行 `go mod vendor` 创建 `vendor` 目录，将构建和测试主模块所有包所需的全部依赖复制到该目录；未被主模块构建或测试引用的依赖则不会被写入。

创建 `vendor` 目录后，可显式指定使用 `vendor` 目录进行离线构建：`go build -mod=vendor`。注意：

- 主模块 `go.mod` 中 `go` 指令为 `go1.14` 或更高版本时，构建命令（`go build`、`go test`、`go run`）不需要显式添加 `-mod=vendor`，只要存在 `vendor` 目录，就会自动使用 `vendor` 目录中的依赖进行离线构建
- 建议在 CI/CD、离线构建、可复现构建等场景显式指定 `-mod=vendor`，以明确构建意图

实践中，使用 vendor 的应用程序项目通常将 `vendor` 目录直接提交到 git 仓库（Kubernetes、etcd 等均采用此做法），这样 clone 代码后即可离线构建，无需额外拷贝依赖；代价是仓库体积变大、依赖升级时 diff 噪音较多。注意这只适用于含 `main` 包的应用程序项目：库项目一般不创建 `vendor` 目录，因为库被其他项目 `import` 时，其 `vendor` 目录会被 Go 忽略。

### vendor 与 GOTOOLCHAIN=local 的关系

`vendor` 和 `GOTOOLCHAIN=local` 解决的是两个不同层面的离线问题：

| 维度 | `-mod=vendor` | `GOTOOLCHAIN=local` |
| ------ | ---------------------------------- | --------------------- |
| 作用层 | 模块依赖源码（第三方库） | Go 工具链本身（编译器、标准库等） |
| 禁用什么 | 强制使用本地 `vendor` 目录，不从网络拉取模块 | 强制使用当前 `${GOROOT}` 目录中的 Go 工具链，不自动下载或切换工具链 |

## 发布模块

Go 模块的发布机制很简洁：在代码仓库中打一个符合版本号格式的 git tag 并推送到远端，即完成发布。没有上传、审核或注册流程，tag 就是版本，Go 的公共模块代理（`proxy.golang.org`）会定期爬取远程仓库的 tag，用户执行 `go get` 时代理自动返回对应版本。发布后如果有人使用 Go 工具下载了它，该模块会自动出现在 [pkg.go.dev](https://pkg.go.dev) 上。

发布模块的前提：`go.mod` 中 `module` 指令声明的模块路径必须是公网可解析的路径（如 `github.com/yourname/your-proj`），否则公共代理无法发现该模块。

### 版本管理流程

[模块发布与版本管理流程](https://go.dev/doc/modules/release-workflow)：

1. 当模块的代码准备好供其他开发者试用时，开始发布 v0 预发布版本，例如 v0.0.0-beta.0
2. 发布一个不保证稳定但用户可以尝试的 v0 版本，例如 v0.0.1，版本号在 v0.x.x 范围内
3. 在你的 v0 版本发布后，你可以继续发布新版本，这些新版本可能包括漏洞修复（补丁发布）、模块公开 API 的补充（小版本），甚至破坏性变更
4. 当你准备稳定版本发布时，会发布预发布版本邀请社区试用，例如 v1.0.0-alpha
5. 发布 v1 作为第一个稳定版本，这是首次对模块稳定性做出承诺的发布，例如 v1.0.0
6. 发布补丁版本（修订版本），只做 bug 修复，例如 v1.0.1
7. 发布非破坏性 API 变更（次版本），添加不破坏现有 API 的新功能，例如 v1.1.0
8. 发布破坏性 API 变更（主版本），例如 v2.0.0。流程为：

当出现破坏性 API 变更时，需要修改主版本号，例如 v2.0.0。从 v2 开始的主版本发布需要额外动作，因为 Go 要求主版本号必须写入模块路径，所以 v2+ 与 v1 是不同的模块。v2 版本发布流程：

- 在仓库中创建 `v2` 分支
- 修改 `go.mod` 中的 `module` 指令，追加主版本后缀，例如 `module github.com/yourname/your-proj/v2`，可用 `go mod edit -module=github.com/yourname/your-proj/v2` 命令修改
- 修改代码中所有内部包的 `import` 语句，例如 `import "github.com/yourname/your-proj/internal"` 改为 `import "github.com/yourname/your-proj/v2/internal"`
- 陆续发布 v2 的预发布版本和正式版本

### 嵌套模块的 tag 前缀

如果一个仓库内有多个模块（多模块开发），每个模块的 tag 需要加目录前缀，用斜杠分隔：`子目录名/版本号`。例如仓库根目录有 `go.mod`（模块 A），子目录 `lib` 下也有 `go.mod`（模块 B），则模块 B 的 tag 应为 `lib/v1.0.0`，而根模块 A 仍用 `v1.0.0`。tag 前缀与 `go.mod` 所在目录的相对路径一一对应。

### 私有模块

公共代理（`proxy.golang.org`）和 `pkg.go.dev` 不会收录私有仓库的模块。私有模块发布后，使用者需要设置环境变量让 Go 绕过公共代理直接从源仓库拉取：

```bash
# 对指定域名下的模块绕过代理，直接拉取
go env -w GOPRIVATE=github.com/yourname

# 效果相同的另一种写法（更精细的控制）
go env -w GONOPROXY=github.com/yourname/your-proj
```

设置后 `go get github.com/yourname/your-proj@v1.0.0` 会直接走 git 而非经过代理。私有模块的发布流程与公共模块完全相同，仍是打 tag、推送，只是消费者拉取方式不同。

### 已发布版本不可变 + retract

Go 模块一旦被公共代理缓存，就不能删除或覆盖。如果你不小心发布了一个有问题的版本，不要删除 tag 后重新打，因为代理已经缓存了原版本的元数据，消费者会持续得到旧版本。

正确做法是撤回（retract）：在模块的 `go.mod` 中添加 `retract` 指令，声明某个版本范围已被撤回，MVS 算法在构建时会自动跳过这些版本。示例：

```go
retract (
    v1.0.1 // 撤回单个版本
    [v1.1.0, v1.1.2] // 撤回区间 v1.1.0 到 v1.1.2 的版本，前后都是闭区间
)
```

`retract` 指令需要在一个新的模块版本中发布，即你要先发布一个 v1.0.2（包含 retract 声明），才能撤回 v1.0.1；可以在 v1.0.2 版本中撤回它自己。

除直接编辑 `go.mod` 外，也可通过 `go mod edit` 命令行方式添加或移除 retract：

```bash
# 撤回单个版本
go mod edit -retract=v1.0.1

# 撤回版本区间（方括号需加引号）
go mod edit -retract='[v1.1.0,v1.1.2]'

# 追加多个撤回
go mod edit -retract=v0.9.0 -retract=v0.9.1

# 取消某个版本的撤回
go mod edit -dropretract=v1.0.1
```

详见[官方撤回指令文档](https://go.dev/ref/mod#go-mod-file-retract)。
