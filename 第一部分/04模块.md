# 模块（Module）

模块是 Go 依赖管理和版本控制的基本单元。一个模块由其根目录下的 `go.mod` 文件定义，该文件定义了这个模块的身份标识、依赖关系和构建规则。

一个模块通常对应一个项目，其中包含若干个库包（可被 `import` 的非 `main` 包）和应用程序包（`main` 包）。

## 核心命令

| 命令 | 作用 | 关键输出文件 |
| --- | --- | --- |
| `go mod init <module-path>` | 初始化模块 | `go.mod` |
| `go mod tidy` | 自动整理依赖 | `go.mod`、`go.sum` |
| `go mod download` | 下载依赖到模块缓存目录 | - |
| `go mod verify` | 验证已下载依赖的校验和 | - |
| `go mod vendor` | 创建 `vendor` 目录，用于离线构建 | `vendor/` |
| `go mod edit` | 以命令行方式编辑 `go.mod` 文件 | `go.mod` |

## go.mod 文件

在要作为模块根目录的目录（通常是项目根目录）执行 `go mod init <module-path>`，即可生成 `go.mod` 文件并初始化模块。

模块路径（module-path）是一个模块的唯一标识，它是一个字符串，不要求必须对应真实 URL。但惯例上使用可解析的域名路径格式：`<域名>/<作者>/<项目>`（例如 `github.com/yourname/your-proj`），便于未来发布和 `go get` 获取。

从 v2 开始，主版本号必须写入模块路径，例如 `github.com/yourname/your-proj/v2`，所以 `.../your-proj` 和 `.../your-proj/v2` 是两个不同的模块。

`go.mod` 是模块定义文件，内容如下（示例）：

```text
// 模块路径，即模块的唯一标识，也是该模块内所有包的导入路径前缀
module example.com/yourname/your-proj

// 模块要求的最低 Go 版本
go 1.24.1

// 依赖的模块及版本
require (
 github.com/gin-gonic/gin v1.12.0
 golang.org/x/text v0.42.0
)

// 本地替换，见多模块开发中的 call-module 示例
replace golang.org/x/text => ../local/text

// 排除模块特定版本，禁止其被 MVS 选中（不常用）：go mod edit -exclude=github.com/somebody/some-proj@v1.0.0
exclude github.com/somebody/some-proj v1.0.0

// 依赖的命令行工具（Go 1.24+）
tool golang.org/x/tools/cmd/stringer

// 间接（indirect）依赖的模块及版本
require (
 golang.org/x/mod v0.41.0 // indirect
 golang.org/x/sync v0.23.0 // indirect
 golang.org/x/tools v0.50.0 // indirect
)
```

模块版本号采用语义化版本：`主版本号.次版本号.修订号`。

### go 指令和 toolchain 指令

`go.mod` 中的 `go` 指令声明模块要求的最低 Go 版本，`toolchain` 指令（Go 1.21+）指定主模块（正在其中执行 `go` 命令的那个模块）建议使用的工具链版本，形如 `toolchain go1.25.0`。

构建时 Go 优先依据 `toolchain` 指令（不存在时依据 `go` 指令）确定工具链版本；默认策略 `GOTOOLCHAIN=auto` 下，若该版本高于本地 `${GOROOT}` 目录安装的 Go 版本，会自动下载并切换到对应工具链。

`toolchain` 指令只在主模块的 `go.mod` 中被读取和生效。当把某个库作为依赖引入当前项目时，这个库的 `go.mod` 中即使写了 `toolchain`，也不会影响当前项目的构建工具链选择。

作为对比，主模块的 `go` 指令版本必须大于或等于所有依赖的 `go` 指令版本，这保证了主模块的工具链不会低于依赖所要求的最低 Go 版本。

向 `go.mod` 中添加 `toolchain` 指令：`go mod edit -toolchain=go1.25.0`，`toolchain` 的建议版本不应低于 `go` 指令声明的版本，否则无效

从 `go.mod` 中移除 `toolchain` 指令：`go mod edit -toolchain=none`，`none` 表示移除

执行 `go mod tidy -go=1.27` 可更新 `go` 指令声明的最低 Go 版本并重新同步（sync）依赖，该命令不会自动更新 `toolchain` 指令。

### require 指令和 replace 指令

当通过 `go get` 添加依赖时，会自动更新 `go.mod` 中的 `require` 指令。`require` 指令记录的是依赖模块的精确版本号（不是范围）。

`indirect` 注释表示间接依赖，即未在项目源码中直接 `import`、因为被其它依赖引用而引入的模块。

执行 `go mod tidy` 会自动整理直接依赖和间接依赖。

当某个依赖的特定版本存在严重缺陷或安全漏洞时，最直接的做法是通过 `go get` 将该依赖模块升级到已修复的版本。若问题版本是被间接引入的，也可以在 `go.mod` 中显式 `require` 已修复的版本，把它“提升”为直接依赖，从而覆盖间接引入的旧版本：

```bash
go get github.com/somebody/some-proj@v1.0.1
```

如果修复不在原仓库，而在本地副本或自己的 fork 中，可以通过 `replace` 指令把有问题的模块重定向过去：

```bash
# 用本地副本替换：模块路径=本地路径
go mod edit -replace github.com/somebody/some-proj=/path/to/local/some-proj

# 用 fork 版本替换：模块路径=fork仓库地址@版本号
go mod edit -replace github.com/somebody/some-proj=github.com/yourfork/some-proj@v1.0.1
```

### tool 指令（Go 1.24+）

在 Go 1.24 之前，Go 缺少统一的标准方式来管理代码生成器、linter 等开发工具。常见的做法是创建一个 `tools.go` 文件，通过空白导入（`import _ "..."`）使这些工具被记录为项目的依赖。

```go
//go:build tools

package tools

import (
 _ "golang.org/x/tools/cmd/stringer"
)
```

Go 1.24 引入的 `tool` 指令让声明工具依赖变得像声明普通库依赖一样直接，其核心是将工具作为项目依赖模块进行版本化管理，确保团队所有成员使用完全相同的工具版本。

[stringer](https://pkg.go.dev/golang.org/x/tools/cmd/stringer) 是 Go 官方 [x/tools](https://pkg.go.dev/golang.org/x/tools) 仓库中的一个常用代码生成工具，它会根据给定类型自动生成 `String()` 方法（实现 `fmt.Stringer` 接口）。下面以 `stringer` 为例，介绍对工具的管理操作。

添加工具：`go get -tool golang.org/x/tools/cmd/stringer@latest`，也可以固定版本，如 `@v0.31.0`。这条命令会把 `stringer` 的源码连同依赖一起下载到模块缓存目录，并在 `go.mod` 中添加相应的 `require` 和 `tool` 指令；它不会编译或安装可执行文件，而是在通过 `go tool` 运行工具的时候按需构建二进制（结果缓存在 `GOCACHE`，不写入 `GOBIN`）并执行

假设项目中有如下 `color.go` 文件，其中定义了一个枚举类型 `Color`：

```go
type Color int

const (
    Red   Color = iota // 0
    Green              // 1
    Blue               // 2
)
```

使用工具：`go tool golang.org/x/tools/cmd/stringer -type=Color`，工具名可简写为 `stringer`。这条命令会生成 `color_string.go` 文件，其中包含 `func (i Color) String() string` 方法

从 `go.mod` 中移除工具：`go get -tool golang.org/x/tools/cmd/stringer@none`，`@none` 表示移除

升级所有工具：`go get tool`，这里的 `tool` 是元模式，表示 `go.mod` 中 tool 指令声明的所有工具

将 `go.mod` 中 `tool` 指令声明的所有工具安装到环境变量 `${GOBIN}` 目录以便全局使用：`go install tool`

## go.sum 文件

`go.sum` 文件记录项目中所有依赖模块的校验和，用于验证模块内容的完整性。内容示例：

```text
github.com/bytedance/sonic v1.9.1 h1:ei0tVql02GmiYGRCTUcI6g...
github.com/bytedance/sonic v1.9.1/go.mod h1:iZcSUejdk5C4OW...
```

每个模块对应两行记录：一行记录模块压缩包的校验和；另一行的版本号带 `/go.mod` 后缀，记录该模块的 `go.mod` 文件的校验和。

`go build`、`go mod tidy` 等命令在下载依赖模块时自动验证校验和，不一致则报错。也可以执行 `go mod verify` 手动验证。

## 依赖管理

### go get 添加依赖

`go get` 添加依赖模块到 `go.mod`，并自动更新 `go.mod` 中的 `require` 指令：

- 指定版本：`go get github.com/BurntSushi/toml@v1.2.0`
- 省略版本表示获取最新版：`go get github.com/BurntSushi/toml`，等价于 `@latest`

标准库的包不需要 `go get`，直接 `import` 导入即可使用。

CI/CD、Docker 构建等需要预先准备环境，可以执行 `go mod download` 将依赖模块提前下载到模块缓存目录。

### go get -u 升级依赖

`go get -u` 只更新次版本和修订版本，不会自动跨越主版本；`go get -u=patch` 更保守，只更新修订版本。

- 更新模块及其依赖到最新版本：`go get -u github.com/BurntSushi/toml`
- 仅更新模块本身到最新版本：`go get github.com/BurntSushi/toml`
- 仅更新模块本身到指定版本：`go get github.com/BurntSushi/toml@v1.5.0`
- `go get -u ./...`：更新当前目录下所有源文件中 `import` 的直接依赖，并因此在重算依赖图时影响间接依赖的版本。`./...` 是路径通配符，`.` 代表当前目录，`...` 代表递归匹配子目录

Go 将 v2+ 版本视为不同的模块（模块路径带 `/v2` 主版本号），需手动 `go get` 并修改源文件中的 `import` 语句。

### go mod tidy 同步依赖

在项目根目录执行 `go mod tidy`：

- 添加缺失模块：自动扫描所有源文件中的 `import` 语句，将构建所需但尚未记录的依赖模块添加到 `go.mod` 文件
- 移除未引用模块：删除 `go.mod` 文件中不再被任何源码引用的依赖模块
- 同步校验文件：同时整理 `go.sum` 文件，添加缺失的校验和记录，移除多余的条目，确保依赖的完整性

建议在修改 `import` 语句后、构建部署前或定期执行 `go mod tidy`，以保持依赖整洁。

### 清理并重新下载依赖

```bash
go clean -modcache
go mod tidy
```

### 查询依赖

| 命令 | 说明 |
| --- | --- |
| `go list -m all` | 列出所有依赖模块及版本，包括间接依赖。展示的是 MVS 最终选择的版本 |
| `go list -m -u all` | 列出所有依赖模块及最新版本（如果有的话） |
| `go list -m -versions <module>` | 列出指定模块的所有版本，示例：`go list -m -versions github.com/gin-gonic/gin` |
| `go list -m -u <module>` | 显示指定模块当前版本及最新版本（如果有的话） |
| `go mod graph` | 查看依赖关系，每行两个字段，用空格分隔，前者依赖后者。展示的是原始的依赖声明（`go.mod` 中的 `require` 指令），并不是 MVS 最终选择的版本 |
| `go mod why <pkg>` | 显示主模块到该包的最短导入路径，输出一条从主模块出发，经过一系列包，最终到达目标包的链路。可查清指定包是在哪里被 import 的 |
| `go mod why -m <module>` | 查找主模块到该模块下任意包的最短导入路径。可查清模块是在哪里被引用的 |

## MVS 版本选择算法

Go 使用最小版本选择（MVS，Minimal Version Selection）算法，为本次构建计算出一份实际使用的模块版本清单，称为 build list（构建列表）。它不是 `go.mod` 里的 `require` 声明，而是 MVS 对所有约束取最高版本后得到的最终结果，可用 `go list -m all` 查看。

MVS 算法：

- 从主模块出发，遍历整个模块依赖图
- 对每个模块，收集所有 `require` 声明的版本约束
- 选取其中最高的版本，作为该模块在 build list 中的版本

版本管理最佳实践：

- 生产环境锁定确切版本，确保每次构建内容一致
- 定期更新依赖模块：`go get -u ./...`
- 保持依赖整洁：`go mod tidy`

> [!NOTE]
> `go get -u ./...` 更新直接依赖，并因此在重算依赖图时影响间接依赖的版本。具体机制是：
>
> 1. `go get -u` 把直接依赖更新到最新版
> 2. 每个直接依赖的最新版 `go.mod` 中声明它自己依赖的模块的最低版本要求
> 3. MVS 重新计算整个依赖图，对每个间接依赖选取所有约束中最高的版本
>
> 所以间接依赖的版本会随之变化，但选中的不是“绝对最新”，而是“满足所有约束的最高版本”。

## vendor 离线构建

`vendor` 用于离线构建。

在项目根目录执行 `go mod vendor` 创建 `vendor` 目录并根据 `go.mod` 和 `go.sum` 下载所有依赖的精确版本到 `vendor` 目录。

创建 `vendor` 目录后，显式指定使用 `vendor` 目录进行离线构建：`go build -mod=vendor`。

- Go 1.14+ 不需要加 `-mod=vendor`，当 `vendor` 目录存在时自动进行离线构建
- 仅建议在 CI、离线、合规场景构建时显式指定 `-mod=vendor`
