# 模块

Go 模块（module）是一组相关包的集合，是 Go 的官方依赖管理系统。模块包含 `go.mod` 文件，用于管理项目依赖和版本控制。

## 核心命令

| 命令 | 作用 | 关键输出文件 |
| -- | -- | -- |
| `go mod init module-path` | 初始化新模块 | `go.mod` |
| `go mod tidy` | 添加缺失的依赖，移除未使用的依赖 | `go.mod`、`go.sum` |
| `go mod download` | 下载依赖到本地模块缓存 | — |
| `go mod verify` | 验证已下载依赖的校验和 | — |
| `go mod vendor` | 创建 `vendor` 目录 | `vendor/` |
| `go mod edit` | 以命令行方式编辑 `go.mod` 文件 | `go.mod` |

## 初始化模块与 go.mod 文件

在项目根目录下执行 `go mod init module-path` 生成 `go.mod` 文件。

建议 `module-path` 遵循 `<域名>/<作者>/<项目>` 的格式，如 `github.com/yourname/your-proj`，便于未来发布。

`go.mod` 是模块定义文件，位于项目根目录，包含以下部分：

```text
// 模块路径，即该模块内所有包的导入路径前缀
module example.com/yourname/your-proj

// 最低 Go 版本要求
go 1.25.4

// 依赖的模块及版本
require (
 github.com/gin-gonic/gin v1.9.1
 golang.org/x/text v0.12.0
)

// 本地替换，见下面的 call-module 示例 todo
replace golang.org/x/text => ../local/text

// 排除特定版本（不常用）
exclude github.com/somebody/some-proj v1.0.0

// 依赖的命令行工具（Go 1.24+）
tool golang.org/x/tools/cmd/stringer

require (
 golang.org/x/mod v0.38.0 // indirect
 golang.org/x/sync v0.22.0 // indirect
 golang.org/x/tools v0.48.0 // indirect
)
```

`go.mod` 中的 `go` 指令表示模块支持的最低 Go 版本。执行 `go mod tidy -go=1.27` 可更新模块支持的 Go 版本并重新同步依赖。

`go.mod` 中的 `require` 指令记录的是依赖的精确版本号（不是范围），配合 `go.sum` 中的校验和实现依赖锁定。`indirect` 注释表示间接依赖。

当得知某个依赖的特定版本存在严重缺陷或安全漏洞时，使用 `exclude` 是最直接有效的规避方法：`go mod edit -exclude=github.com/somebody/some-proj@v1.0.0`。

先 `exclude` 有问题的版本，再 `replace` 指向修复后的本地副本或 fork 版本：

```bash
# 用本地副本替换有问题的版本
go mod edit -replace github.com/somebody/some-proj=/path/to/local/some-proj
# 用 fork 版本替换有问题的版本
go mod edit -replace github.com/somebody/some-proj=github.com/yourfork/some-proj@v1.0.1
```

## tool 指令（Go 1.24+）

在 Go 1.24 之前，管理代码生成器、linter 等开发工具一直是个难题。常见的做法是创建一个 `tools.go` 文件，通过空白导入使 Go 模块系统误认为这些工具是项目的依赖。

`tool` 指令让声明工具依赖变得像声明普通库依赖一样直接。它的核心是将工具作为项目依赖进行版本化管理，确保团队所有成员使用完全相同的工具版本。

[stringer](https://pkg.go.dev/golang.org/x/tools/cmd/stringer) 是 Go 官方 [x/tools](https://pkg.go.dev/golang.org/x/tools) 仓库中的一个常用代码生成工具，它会根据给定类型自动生成 `String()` 方法，方便调试和日志输出。下面以 stringer 为例，介绍对该工具的管理操作。

添加工具：`go get -tool golang.org/x/tools/cmd/stringer@latest`，也可以固定版本，如 `@v0.31.0`。这条命令会下载 stringer 及其依赖，并在 `go.mod` 中添加 `require` 和 `tool` 指令。

假设项目中有如下 `color.go` 文件，定义了一个枚举类型：

```go
type Color int

const (
    Red   Color = iota // 0
    Green              // 1
    Blue               // 2
)
```

使用工具：`go tool golang.org/x/tools/cmd/stringer -type=Color`，工具名可简写为 stringer。这条命令会生成 `color_string.go` 文件，其中包含 `func (i Color) String() string` 方法。

移除工具：`go get -tool golang.org/x/tools/cmd/stringer@none`，`@none` 表示移除。

升级所有工具：`go get tool`

将 `go.mod` 中所有 tool 指令列出的工具安装到环境变量 `${GOBIN}` 目录以便全局使用：`go install tool`

## go.sum 文件

`go.sum` 文件记录项目依赖模块的校验和，用于验证模块内容的完整性。文件内容示例：

```text
github.com/bytedance/sonic v1.9.1 h1:ei0tVql02GmiYGRCTUcI6g...
github.com/bytedance/sonic v1.9.1/go.mod h1:iZcSUejdk5C4OW...
```

`go build`、`go mod tidy` 等命令在下载依赖时自动验证校验和，不一致则报错。也可以执行 `go mod verify` 手动验证。

## 依赖管理

`go get` 添加依赖到 `go.mod`：

- 指定版本：`go get github.com/BurntSushi/toml@v1.2.0`
- 省略版本表示获取最新版：`go get github.com/BurntSushi/toml`，等价于 `@latest`

标准库的包不需要 `go get`，直接 `import` 导入使用。

CI/CD、Docker 构建等需要预先准备环境的阶段，可以使用 `go mod download` 命令将当前项目所需的依赖提前下载到本地的模块缓存目录 `${GOMODCACHE}` 中。

升级依赖：模块版本号采用语义化版本 `主版本号.次版本号.修订号`，`go get -u` 只更新次版本号和修订号，不会自动跨越主版本号。

- 更新到最新版本：`go get -u github.com/BurntSushi/toml`
- 更新到指定版本：`go get github.com/BurntSushi/toml@v1.5.0`
- 更新所有依赖：`go get -u ./...`，更新当前目录下所有包中 `import` 的依赖。`./...` 是路径通配符，`.` 代表当前目录，`...` 代表递归匹配子目录

Go 将 v2+ 版本视为不同的模块（导入路径带 `/v2`），需手动 `go get` 并修改源代码中的 `import` 语句。

同步依赖：在项目根目录执行 `go mod tidy` 扫描项目中的所有源文件，添加缺失的依赖并移除未使用的依赖，同时更新 `go.sum`。建议在修改 `import` 语句后、构建部署前或定期执行 `go mod tidy`，以保持依赖整洁。

清理并重新下载依赖：

```bash
go clean -modcache
go mod tidy
```

查询依赖：

| 命令 | 说明 |
| -- | -- |
| `go list -m all` | 列出所有依赖 |
| `go list -m -u all` | 列出所有依赖及可用更新 |
| `go list -m -versions <module>` | 列出特定模块的所有版本，示例：`go list -m -versions github.com/gin-gonic/gin` |
| `go list -m -u <module>` | 列出特定模块的最新版本 |
| `go mod graph` | 查看依赖图 |
| `go mod why <module>` | 查看特定模块的依赖关系链 |

## MVS 版本选择算法

Go 使用最小版本选择（MVS，Minimal Version Selection）算法：

- 首先列出项目所有依赖对同一个模块声明的版本要求
- 如果只有一个版本要求，就直接用它
- 如果有多个不同的版本要求，则选择其中最高的版本，以保证所有依赖都能正常工作

版本管理最佳实践：

- 生产环境锁定确切版本，确保每次构建内容一致
- 定期更新依赖：`go get -u ./...`
- 保持依赖整洁：`go mod tidy`

> [!NOTE]
> `go get -u` 只更新直接依赖，间接依赖的版本受限于引入它的直接依赖的 `go.mod` 约束。

## vendor 离线构建

`vendor` 用于离线构建。在项目根目录下执行 `go mod vendor` 创建 `vendor` 目录并根据 `go.mod` 和 `go.sum` 下载所有依赖的精确版本到 `vendor` 目录。

创建 `vendor` 目录后，显式指定使用 `vendor` 目录进行离线构建：`go build -mod=vendor`。

- Go 1.14+ 不需要加 `-mod=vendor`，`vendor` 目录存在时会自动离线构建
- 仅建议在 CI、离线、合规场景构建时显式指定 `-mod=vendor`
