# 包（Package）

包是 Go 代码组织与复用的基本单元，也是编译的最小单元，一个包中的所有非测试源文件一起被编译为一个编译归档（`.a` 文件）并缓存在构建缓存中。

- 每个源码目录（不包括子目录）对应一个包，包名通常与目录名保持一致。与目录层级不同，包之间没有父子层级关系，例如 [encoding/json](https://pkg.go.dev/encoding/json) 和 [encoding](https://pkg.go.dev/encoding) 是两个独立的包，前者并非后者的子包
- 每个源文件必须通过 `package` 关键字声明自己所属的包，编译器不会根据源文件所在的目录自动推断。`package` 声明不加双引号，只写包名（惯例上与源文件所在的最后一级目录名一致），例如 `package repository`
- 一个目录下的所有非测试源文件必须属于同一个包
- 一个目录下的测试文件可以属于不同的包，例如名为 `foo` 的包中的测试文件可以属于 `foo` 包（`package foo`，白盒测试，能访问未导出标识符），也可以属于 `foo_test` 包（`package foo_test`，黑盒测试，仅能访问导出标识符）
- 应用程序入口文件（其中包含 `main()` 函数）必须位于 `main` 包中

示例：

```text
hello-world/
├── foo
│   ├── bar_test.go
│   ├── foo.go
│   └── foo_test.go
├── go.mod
└── main.go
```

```go
// foo.go，属于 foo 包
package foo

func Add(a, b int) int {
 return a + b
}

// foo_test.go，属于 foo 包
package foo

import "testing"

func TestAdd(t *testing.T) {
 if Add(1, 2) != 3 {
  t.Errorf("Add(1, 2) = %d; want 3", Add(1, 2))
 }
}

// bar_test.go，属于 foo_test 包
package foo_test

import (
 "testing"

 "example.com/hello-world/foo"
)

func TestFoo(t *testing.T) {
 if foo.Add(1, 2) != 3 {
  t.Errorf("Add(1, 2) = %d; want 3", foo.Add(1, 2))
 }
}
```

## 包的命名

包名（源文件的 `package` 声明指定的名称）通常与源码目录名保持一致（`main` 包、测试包除外），应短小精悍、含义明确。命名规则如下：

- 只能包含字母（建议 ASCII 字母）、数字、下划线，不能以数字开头
- 使用全小写单词，单词之间不使用下划线或中划线分隔，所有单词连写在一起（测试包除外，测试包名以 `_test` 为后缀，例如 `package foo_test`）
- 合理缩写，避免使用过长的单词：
  - 优先采用业界约定俗成、广泛使用的缩写，例如 `fmt`（format）、`strconv`（string conversion）、`io`、`os`、`http`、`db`、`json`、`url`
  - 不随意自创缩写，缩写后仍应含义清晰、便于阅读
  - 同一项目内缩写风格保持一致
- 使用简洁的单数名词，不使用复数（与关键字或预定义标识符有冲突时除外）
- 不使用 `util`、`common`、`misc`、`helper`、`base` 等过于宽泛的名字

示例：

- `strconv` 为 string conversion 两个单词的缩写并连写在一起，不使用下划线或中划线 `str_conv`
- `main` 包名固定为 `main`，其所在的目录名通常不叫 `main`

例外情况：

- 标准库的 [bytes](https://pkg.go.dev/bytes)、[errors](https://pkg.go.dev/errors) 和 [strings](https://pkg.go.dev/strings) 包名使用复数是为了避免和预定义类型 `byte`、`error`、`string` 冲突
- 标准库的 [go/types](https://pkg.go.dev/go/types) 包名使用复数是为了避免和 `type` 关键字冲突

## 导出规则

包中大写字母开头的标识符是导出的，小写字母开头的是未导出的。导入一个包后，只能访问该包导出的标识符。

API 最小导出原则：仅导出外部需要的类型、函数等标识符，内部实现全部以小写字母开头。

无法导入 `main` 包，故 `main` 包通常不应导出任何标识符。

## 导入方式

在包外必须先导入（`import`）包，才能通过包名前缀访问该包导出的标识符。包名前缀本质上是一种命名空间机制，在不同包中可以定义同名的标识符，通过包名前缀加以区分，避免命名冲突。示例：

- `fmt.Println`：访问 `fmt` 包中的 `Println` 函数
- `math.Pi`：访问 `math` 包中的 `Pi` 常量
- `image.Decode`：访问 `image` 包中的 `Decode` 函数
- `utf16.Decode`：访问 `unicode/utf16` 包中的 `Decode` 函数

导入必须以包为单位，不能只导入某个源文件或只导入某个函数、类型等。

导入包的语法：`import "package-path"`

导入路径（包路径，package-path）由“模块路径”（模块定义文件 `go.mod` 中 `module` 指令声明的值）加上“该包在模块中的子目录路径”组成；标准库包的导入路径不含模块前缀，就是其源码目录名，如 `net/http`。

导入的包的包名由该包源码中的 `package` 声明决定，与导入路径通常无关。惯例上包名与导入路径中代表目录名的最后一个元素一致；当最后一段是模块的版本后缀（如 `/v2`）时，包名取其前面的部分。例如 `import "rsc.io/quote/v4"` 导入的包名为 `quote`，通过 `quote.` 访问该包中导出的标识符。

四种导入方式：

| 导入方式 | 语法 | 示例 |
| --- | --- | --- |
| 标准导入 | `import "package-path"` | `import "fmt"`，通过 `fmt.Println()` 访问 |
| 别名导入 | `import alias "package-path"` | `import f "fmt"`，通过 `f.Println()` 访问，适用于包名冲突或简化长包名的场景 |
| 空白导入 | `import _ "package-path"` | `import _ "github.com/go-sql-driver/mysql"`，仅触发被导入包的初始化（自动执行其中的 `init()` 函数）或仅让模块系统记录依赖关系，不直接使用该包导出的标识符 |
| 点导入/省略导入 | `import . "package-path"` | `import . "fmt"`，可直接使用 `Println()` 而无需包名前缀。会污染当前命名空间，不建议使用 |

### 分组导入

使用小括号将导入的包分组，每个包路径占一行：

```go
import (
 "fmt"
 "time"
)
```

分组顺序约定：按“标准库包”、“第三方库包”、“本项目内部包”的顺序分组，组之间用一个空行分隔。

```go
import (
 "fmt"
 "net/http"

 "github.com/gin-gonic/gin"

 "myproject/pkg/config"
)
```

### 循环导入问题

Go 不允许循环导入，例如 A 导入 B，B 又导入 A，编译时会报 `import cycle not allowed` 错误。解决办法：

- 提取公共代码到新包：将 A 和 B 共同依赖的代码提取到独立的包 C 中，打破循环
- 重新划分包边界：两个包联系过于紧密、无法提取公共代码时，合并为一个包或调整职责划分

## 包的初始化

每个包在被应用程序或其它包导入时都会执行一次初始化，整个过程在程序启动时由 Go 运行时自动完成。完整的初始化顺序：

- 导入的依赖包（按依赖关系递归处理，每个包只初始化一次）
- 当前包级常量、变量初始化（按声明顺序和依赖关系）
- 当前包的 `init()` 函数

注意：每个包在一次程序运行中只会初始化一次。

## 包注释（包文档）

- 位于包中任一源文件的 `package` 声明之前，注释块与 `package` 声明语句之间不能有空行
- 只需在包内的一个源文件中书写包注释，通常是主文件或 `doc.go`，包注释很大时就放到一个独立的 `doc.go` 文件中（该文件仅含包注释与 `package` 声明）
- 多个源文件中都有包注释时，`go doc .` 会按源文件名的字典序将它们合并为一份包文档（不推荐，因为最终的包文档受文件名的字典序影响）
- 包注释的第一句以 `Package <包名>` 开头并以句号结尾，作为包的摘要，后续段落补充细节

示例：

```go
// Package mypackage provides awesome functionality.
// More detailed description here...
package mypackage
```

## import 格式化工具

- [goimports](https://pkg.go.dev/golang.org/x/tools/cmd/goimports)：自动管理包导入语句，包括自动添加缺失的 `import` 语句、自动移除未引用的 `import` 语句、对 `import` 语句进行分组和排序。安装：`go install golang.org/x/tools/cmd/goimports@latest`，使用：`goimports -w .`
- [gci](https://github.com/daixiang0/gci)：控制导入顺序并使其始终具有确定性，比 goimports 支持更多自定义选项。安装：`go install github.com/daixiang0/gci@latest`，使用：`gci write --custom-order --section standard --section default --section "prefix(github.com/yourname/your-proj)" .`，prefix 中的 `github.com/yourname/your-proj` 是模块路径

`goimports`、`gci` 这些代码格式化工具也可以集成到 `golangci-lint` 中。

## internal 包

`internal` 是一个特殊的目录名，位于其下的包称为内部包，内部包只能被该 `internal` 目录的父目录的子树中的代码导入。

示例：

```text
proj/
├── a
│   ├── internal
│   │   ├── x
│   │   └── y
│   └── p
└── b
    └── q
```

`internal` 的父目录是 `a`，所以 `a/**/*.go`（`**` 表示任意层级、包括 0 层的目录）中都能导入 `a/internal/x` 这个内部包，具体包括：

```text
a/p/*.go 
a/internal/y/*.go
```

`b` 不在 `a` 的子树中，所以 `b/q/*.go` 不可导入 `a/internal/x`。

Go 支持嵌套的 `internal` 目录，每个 `internal` 目录中的内部包的可见范围均独立计算，判断依据始终是每个 `internal` 目录的父目录。

```text
proj/
├── a
│   ├── internal          # 父目录是 a，内部包的可见范围：a/**/*.go
│   │   ├── x
│   │   └── sub
│   │       └── internal  # 父目录是 a/internal/sub，内部包的可见范围：a/internal/sub/**/*.go
│   │           └── y
│   └── p
└── b
```

## 包的设计原则

- 按逻辑拆分文件，提高可读性：例如 `net/http` 包按其功能拆分为 `client.go`、`server.go`、`cookie.go` 等文件
- 按职责组织而非按数据模型：将类型定义在使用处附近，避免为集中存放数据结构而单独创建 `model` 或 `types` 包
- 避免过早拆分：项目初期不必急于创建大量包，先在一个包中把功能写清楚，等职责边界自然浮现后再拆

参考：[标准 Go 项目结构](https://github.com/golang-standards/project-layout)。
